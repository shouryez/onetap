Cache decision
Every past answer is stored with ~10 rewordings as vectors (lists of numbers that capture meaning). A new complaint is turned into a vector the same way and compared with all of them. If similarity is above τ = 0.87, the stored plan is reused with no AI call.

Similar wording isn't enough: "Wi-Fi keeps turning on" and "…off" score 0.96 but need opposite fixes. The Symptom-Signature Guard also compares the symptom, the context (charging, camera…) and on/off direction, and rejects look-alikes.

Deeplink resolution
Samsung's catalog has 577 Settings deeplinks. For each Settings action: first an exact screen match on the deepest screen named in the steps (e.g. "Navigation bar", not its parent "Display"). If that fails, a keyword + meaning search finds candidates, and a small model chooses one by ID. Code copies the link exactly, so a link can never be made up. On/off direction is respected (enable → "onURL"). A generic placeholder is used only for a real Settings screen that has no catalog entry.
Deeplink decisions appear here.
Grounding check
The article is split into numbered sentences and the model must cite the sentence behind each step. Code then checks that the step's key words really appear there. Steps that fail are dropped, as are invented UI elements and "outcome" sentences. If the article doesn't address the complaint, OneTap returns no match instead of guessing.
